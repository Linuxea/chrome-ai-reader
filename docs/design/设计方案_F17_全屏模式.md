# 设计方案：全屏模式（F17）

> 状态：已实现（2026-11-28）。侧边栏形态完全保留，本方案只做"加法"。

## 1. 结论摘要

产品形态从"侧边栏一种"扩展为"侧边栏 + 全屏标签页两种"，两种形态**实时同步同一份对话**：

- 侧边栏 Header 新增"全屏模式"按钮（Maximize2 图标），点击在当前窗口开一个新标签页
  `src/panel/index.html?full=1&tab=<对话所在标签页 id>`，当前对话无缝续聊
- 全屏页是常规 AI Chat 布局：左侧历史会话列表 + 新建聊天，左下角设置/笔记/主题入口，
  右侧对话区（窄幅居中，复用现有 MessageList / Composer / QuickActions 等全部组件）
- 同步模型：两个页面（surface）绑定**同一个真实标签页 id**，共用 `chrome.storage.session`
  里的同一份 `TabState_<id>`；对端写入经 `storage.onChanged` 字段级合并，流式回答经
  runtime 消息中继镜像，`isGenerating` 作为跨页互斥锁，停止按钮跨页转发
- manifest 零改动（复用同一 HTML，`chrome.tabs.create` 不需要新权限）

## 2. 关键决策（用户已确认）

| 决策点 | 选择 | 备选与否决理由 |
|---|---|---|
| 打开形态 | 当前窗口新标签页 | 独立 popup 窗口（否决：更像"一个网站"以外的应用窗口，用户明确选了标签页） |
| 会话携带 | 两侧实时同步 | 复制分叉（否决：体验断裂）；不携带（否决：脱离时丢上下文） |
| 设置入口 | 打开现有设置页 | 全屏内嵌设置面板（否决：要跨页面重宿主整个 options 应用，v1 工作量不成比例） |

## 3. 架构

### 3.1 为什么绑定真实标签页 id（而不是虚拟空间 id）

同步模式的最大红利：全屏页绑定 URL 里的 `tab=<id>`（真实标签页），于是——

- 页面提取、引用跳转（`jumpToParagraph`）、划词笔记、沉浸式开关、深度批注
  全部原样工作，它们本来就打"活动标签页"，此处即对话所在页
- `chrome.tabs.onRemoved` / `onUpdated` 的缓存失效逻辑零改动
- stores / history-ops / chat-save / stream-controller / TTS / 播客 / 测验全部按
  tab id 键控，免改

代价与对策：全屏页自己也是一个标签页，`initState` 的 `tabs.query({active:true,
currentWindow:true})` 会解析到它自己 → `initState({bindTabId})` 显式绑定（state.ts，
6 行可选参数）。全屏页**不注册** onActivated 监听（对话是"钉住"的，浏览器切页不许拽走聊天）。

### 3.2 同步协议（`panel/lib/sync.ts`）

**状态复制**：核心态每次变更本就持久化到 session 存储（消息边界立即、字段 250ms
防抖）。对端的 `storage.onChanged` 监听只处理 `tabState_<active>` 键，**字段级原地
合并**——绝不替换 TabState 对象引用（history-ops 的原地变更契约、流收尾持有的引用
都必须继续有效）。apply 从不回写（`storage.onChanged` 不在写方触发，天然无回声环）。

**在途标志的所有权规则**：
- `isGenerating`：owner（打开了 ai-chat port 的页面，`ownsGeneration` = abort 注册表）
  永不采纳远端值（被动页自愈的 false 落盘不能取消一条活流）；被动页采纳（形成跨页
  忙锁——第二个窗口无法向同一对话再发消息）
- `quizSession`：双**方都**不在测验中才整体应用（测验流随页面死）；owner 的最终
  提交之后照常经状态复制到达对端
- `isPodcastGenerating`：完全不同步（播客音频是每窗口的 WebAudio，跨页锁没有意义）

**流式中继**：owner 的 `stream-controller` 把 port 事件原样转发
（`sync.streamStart/stream/streamEnd`，fire-and-forget，无接收方时静默）；被动页镜像进
自己的 stream-store —— 两个窗口**同时看着字往外蹦**。终局语义：`done` 的正史由 owner
写入（appendMessage + 立即持久化），被动页的镜像在状态复制到达时清掉；
`error/aborted` 的镜像**保留**（它承载失败重试卡片，与 owner 一致）。被动页收到
`sync.stopRequest` 时**只有 owner 响应**——被动页绝不能碰 `_pendingAborts`
（垃圾挂起中止会被自己下一次发送误吞）。

**启动收养**：`restoreTabState` 剥离在途标志的历史前提（"写方必死"）不再成立——
全屏页可能在对端回答到一半时打开。liftoff 在 init 后读原始存储值，`isGenerating`
为真则收养（配合下面的自愈停止，卡死最多一次点击解除）。

**停止转发**（`requestGenerationStop`，Composer 的唯一停止入口）：
- owner：直接 `abortGeneration`（与 F17 之前逐字节一致）
- 被动页：广播 `sync.stopRequest`；`STOP_RELAY_GRACE_MS`（800ms）内无人认领
  （owner 页已死，留下脏标志）则本地自愈清旗——自愈写的 false 对活着的 owner 无害
  （owner 不同步该标志）

### 3.3 记录写竞争（新引入的防护）

两个页面各有一条 `_saveQueue`，对同一条 IndexedDB 记录做 get→put 读改写会丢更新
（owner 收尾存档 × 被动页改名的瞬间，答案可能丢）。`chat-save.ts` 的
`writeChat` / `syncChatTitleToRecord` 用 **Web Locks**
（`navigator.locks.request('chat-record:<id>')`）做跨上下文互斥；jsdom 无 LockManager
时直通（测试不受影响）。

### 3.4 侧边栏兼容（"旧形态不破坏"）

- App 的 effect 抽成 `hooks/usePanelLiftoff`（两页共用），侧边栏语义不变：仍跟随
  标签页切换、仍消费 F8 右键菜单队列
- 唯二的新行为，都是修 UX 陷阱：
  1. **切到全屏标签页时跳过切换**——否则点开全屏的瞬间侧边栏空白
     （`fullscreenLinkedTabOf` 解析 URL 判定）
  2. **在全屏页聚焦时打开侧边栏（Alt+S）**：`tabs.query` 解析到全屏页自身 →
     liftoff 改绑 URL 里携带的对话标签页，侧边栏直接显示正在聊的内容
- 收养脏旗的场景原本就存在（面板崩溃重开），只是从"永远静默剥离"变成
  "收养 + 一次点击自愈"——多页世界里剥离反而错（会导致双开流）

### 3.5 布局（`FullscreenApp.tsx` + `.fs-*` CSS）

```
.fs-root（row）
├─ .fs-sidebar 264px：品牌 / 新建聊天 / HistoryList（与历史 Sheet 共用组件，
│   当前会话高亮）/ 底部：笔记（开 Sheet）、主题、设置（openOptionsPage）
└─ .fs-main：ConversationTitle（与 Header 共用，行内重命名）
   ├─ QuickActions / TtsIndicator
   └─ .fs-main-col（max-width 900 居中）：MessageList / Quiz / Podcast / Composer
overlay：Sheets / ShareModal / Toasts（position:absolute，天然适配）
```

新建对话抽成 `lib/new-chat.ts`（`startNewChat`），Header 与全屏侧栏同一实现。

## 4. 明确不同步的（像两台设备）

- 草稿与待发图片/标签（每窗口私有）
- 建议问题 chips（每页瞬态 UI）
- 图片 data URL：持久化本就剥离（`stripImagesForPersistence`），同步后对端显示与
  重载一致的"图片已失效"占位，而不是凭空消失
- 每窗口的 TTS 播放/播客音频（WebAudio 是窗口资源，本就如此）

## 5. 已知边界（v1 接受）

- 对端在中途打开（detach 于回答进行中）：镜像流从第一个中继事件起显示，之前的
  内容在终局时由正史补全（短暂的部分→完整跳变）
- owner 处于提取阶段（发消息后、port 打开前约 1–3s）时被动页的停止请求无人认领
  ——`ownsGeneration` 此刻还是 false。等流真正开始再停即可
- 草稿在两个窗口各自保留（合入时以先发送者为准）
