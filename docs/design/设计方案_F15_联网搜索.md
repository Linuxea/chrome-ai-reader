# 设计方案：DeepSeek 原生联网搜索（F15）

> 输入：用户口头需求（本会话对话），无独立意图文档，需求编号由本方案提炼
> 代码基线：main 分支工作区（2026-11-23，`4fc79d9`）
> 参考项目：`/home/linuxea/vibe-projects/talktome`（纯语音产品，已接入 `deepseek_web_search`）
> 已确认决策：① 搜索是常态需求，默认开启，是否搜索由模型逐问判断；② 开关放输入框，发送按钮左侧；③ 智能体模式将废弃，搜索开启时优先走搜索，不做共存界面；④ thinking 不改，也不做「快速模式」；⑤ 只使用 DeepSeek 官方接口的 `deepseek-flash`，不为其他接口做探测和降级
> 状态：**已实现并验证**（2026-11-23）。§1 到 §10 是设计与实测；实施中有两处对设计的小幅调整（来源角标放在句号之后、正文出现前的断流自动重试一次），都记在 §11

## 1. 结论摘要

在现有聊天链路上加一个默认开启的能力：每条聊天消息都向 DeepSeek 声明 `deepseek_web_search` 工具，由模型判断这一问要不要联网。搜索在 DeepSeek 服务端完成，扩展不执行任何工具，也不需要新权限和新依赖。

改动分三块：

- **后台**负责声明工具，并附上提示规则和日期提醒。
- **面板**在输入框放一个开关，并把流式进度和来源引用展示出来。
- **来源角标**只在渲染层生成，所以复制、朗读、分享图片拿到的仍然是干净正文。

阶段 0 的实测回答了两个最不确定的问题。第一，模型没有过度搜索：文章能答的五个问题一次都没触发搜索，需要时效信息的五个问题全部触发了。第二，多轮对话只回传正文没有被接口拒绝，历史存储不用改。

实测还推翻了两个此前的判断。函数工具和联网工具可以放在一起声明，接口没有拒绝，所以「搜索优先于智能体」是产品选择，不是接口限制。深度思考搜索的耗时是 5 到 11 秒，不是担心的分钟级，所以不用放宽超时。

因为只用 `deepseek-flash`（决策 ⑤），接口能力探测、降级重发、开关的「不支持」状态都不做。换成别的接口或模型时会直接看到接口的报错，这是已知并接受的取舍（§5.6）。

## 2. 需求清单（本方案提炼编号）

### 规则

| 编号 | 内容 |
|---|---|
| R-01 | 设置项 `webSearch` 默认 `true`。输入框的开关和设置页的勾选框都能改它，两处保持同步 |
| R-02 | 只有聊天主线声明工具（`ai-chat` 端口上的普通对话）。追问建议、播客脚本、批注、翻译、出题、大纲都不声明 |
| R-03 | 声明方式固定为 `tools: [{ type: 'deepseek_web_search' }]`。不传 `web_search_options` 和 `tool_choice`，不改 thinking、temperature、`stream_options` |
| R-04 | 工具声明、提示规则（一条 system 消息）、`latest_reminder` 三者绑在一起，由后台决定，要么都发，要么都不发 |
| R-05 | `latest_reminder` 的内容是 `YYYY-MM-DD,<星期>,,Web,<语言>`：日期和星期取本机时区，地点留空，语言跟随界面语言。它插在最后一条 user 消息之前 |
| R-06 | 流式过程中，`server_tool_event` 转成端口消息，回答上方实时显示搜索过程 |
| R-07 | 回答结束后，`annotations` 里的引用变成正文内的编号角标。点击角标在新标签页打开来源。角标和 `[#N]` 段落引用的样式必须能区分 |
| R-08 | 搜索过程和来源随 assistant 消息持久化（本地字段 `web`），不回传模型。重载历史、切换分支之后仍然能渲染 |
| R-09 | 进度事件必须产出 delta，让现有的 90 秒空闲看门狗在搜索期间保持续命。超时时长不改 |
| R-10 | 搜索开启时，请求一律走普通聊天加搜索，不走智能体。这是产品选择（见 §5.7） |
| R-11 | 文案 zh / en 双语；提示词进 `prompts.ts`；不新增依赖，不改 manifest |
| R-12 | 角标只存在于渲染层。复制、朗读、分享图片、导出 Markdown 得到的文本里不能出现占位符 |
| R-13 | 接口拒绝工具时不探测、不记忆、不降级，按现有的错误卡片显示接口的报错原文 |
| R-14 | README 和设置页提示里的模型名统一写成 `deepseek-flash`（README 现在写的是 `deepseek-chat`） |
| R-15 | 聊天流在产出任何正文之前断掉（连接中断，或接口在流里报错）→ 后台自动把同一个请求重发一次，面板丢弃上一次已收到的思考和搜索事件并提示。已有正文之后、接口返回了 HTTP 状态码、空闲超时、端口已关闭这四种情况不重试（实施中新增，见 §11） |

### 边界情况

| 编号 | 内容 |
|---|---|
| E-01 | 接口拒绝工具（换了模型或接口）→ 错误卡片显示报错原文；关掉开关后恢复。实测 `deepseek-v4-pro` 就会这样 |
| E-02 | 用户关闭了搜索 → 不声明工具，也不发规则和日期提醒，行为和现状一致 |
| E-03 | 模型判断不需要搜索（例如「总结这篇文章」）→ 没有进度事件，没有角标，没有过程行。实测这时连 `step_reasoning_done` 都不会发 |
| E-04 | 流中途停止、断开或出错时已经有正文 → 保留部分回答，过程行用已收到的事件；还没有正文 → 走现有的 aborted / error 路径 |
| E-05 | 生成失败：末块带 `error`，`choices` 为空，没有 `[DONE]` → 现有的 `json.error` 分支抛错 |
| E-06 | `finish_reason: content_filter` → 现有的 refusal 处理 |
| E-07 | 引用偏移落在 Markdown 定界符内侧（比如加粗符号里面）→ 插入点后移到定界符之后；落在链接地址里 → 后移到右括号之后；偏移越界 → 丢弃这条引用 |
| E-17 | 引用范围在句子的收尾标点之前结束（实测捕获的 7 条引用全部如此）→ 角标放在标点之后，读作「……API”。¹」；ASCII 句点后面不是空白时不后移，避免把 `3.14`、`e.g.` 当成句末（实施中新增，见 §11） |
| E-08 | 多条引用指向同一段正文，或者同一个网址被引用多次 → 同一位置连续放多个角标；来源按网址去重，编号按首次被引用的顺序 |
| E-09 | 某次搜索调用失败（`call_completed` 带 `status: 'failed'` 和 `error`）→ 过程行标出失败，不影响正文 |
| E-10 | 图片搜索结果带 `image_url` → 不展示远程图片（沿用「远程图片不加载」的规则），只显示标题 |
| E-11 | 历史里含有智能体模式留下的函数工具消息 → 实测接口接受（§6 的 E3b），不需要特殊处理 |
| E-12 | 生成过程中点击开关 → 允许，只影响下一条消息 |
| E-13 | 当前页面没有正文（`chrome://` 等不能注入的页面）→ 规则文案要在没有文章时也成立 |
| E-14 | 智能体模式和搜索同时开着 → 智能体不再生效（已确认接受） |
| E-15 | `call_completed` 事件可能乱序到达（实测同一步的第 2、3 个先于第 0、1 个）→ 按事件里的 `call.id` 归位，不按顺序 |
| E-16 | 接口类型选了 Anthropic（这条代码路径还在）→ Anthropic provider 不认识搜索请求，等同关闭，不报错 |
| E-18 | 流在正文出现之前断掉 → 按 R-15 自动重试一次；重试仍失败 → 错误卡片，可手动重发 |
| E-19 | 流在正文出现之后断掉 → 不重试，错误卡片（沿用原有行为） |

## 5. 设计方案

### 5.1 数据流

```
输入框开关（读设置 webSearch，默认开）
  → send.ts            callAI(messages, tabId, { agent, webSearch })
  → ai-chat 端口       AIChatRequest.webSearch
  → chat-runner        组装「规则 + 日期提醒」交给 provider
  → openaiProvider     声明工具
       ← server_tool_event      → search_event   → 面板实时显示搜索过程
       ← 末块 annotations 等    → finish.web     → done.web
  → 面板               过程行 + 角标；把 web 挂到 assistant 消息上持久化
```

### 5.2 协议与类型

**`src/shared/types.ts`**（叶子模块，只放数据形状）

```ts
interface WebSource { url: string; title: string; siteName?: string }
/** 一次服务端工具调用：搜索、打开网页或页内查找。 */
interface WebStep {
  id: string;
  kind: 'search' | 'deep_search' | 'image_search' | 'deep_image_search';
  action: { type: 'search'; queries: string[] } | { type: 'open_page'; url: string }
        | { type: 'find_in_page'; url: string; pattern: string };
  status: 'completed' | 'failed';
  sources?: WebSource[];                         // 仅搜索：这次调用拿到的结果
  page?: { url: string; title: string | null };  // 仅打开网页 / 页内查找
}
/** start / end 是正文里的 Unicode 码点偏移；source 是 sources 的下标。 */
interface WebCitation { start: number; end: number; source: number }
interface WebResult {
  steps: WebStep[];
  sources: WebSource[];      // 被引用的来源，按网址去重
  citations: WebCitation[];
  searches: number;          // 搜索调用数
  pages: number;             // 打开过的不同网址数
}
// ChatMessage 增加：web?: WebResult
```

`web` 和 `agentTrace`、`finish` 一样是本地字段：随消息存进会话存储和 IndexedDB，`toApiMessage` 不会把它发回模型。步骤里的 `signature` 和每一步的 `reasoning_content` 不保存。

**`src/shared/protocol.ts`**

```ts

```

### 5.3 Service Worker

**`providers/types.ts`**：`ChatRequest` 增加 `webSearch?: { rule: string; reminder: string }`。规则和日期提醒的文本由 `chat-runner` 准备好传进来，provider 只负责在声明工具时把它们放进请求。`ChatDelta` 增加 `{ type: 'search_event'; event }`，`finish` 增加 `web?`。

**`providers/openai.ts`**：

1. `build()` 在请求要求联网时声明工具，同时做两件事：在开头连续的 system 消息之后插入规则；在最后一条 user 消息之前插入 `latest_reminder`。
2. `handle()` 解析 `choice.server_tool_event`，逐条产出 `search_event`。三种事件都产出，`step_reasoning_done` 的作用是让看门狗续命，runner 不转发它。
3. 末块的 `delta.server_tool_calls` 和 `delta.annotations` 交给 `buildWebResult()`，结果挂在 `finish` 上。

**`chat-runner.ts`**：

- `RunOptions` 增加 `webSearch?: boolean`。它读取 `language` 设置，用 `getPrompt('websearch.rule', lang)` 和 `buildLatestReminder(lang)` 组装出交给 provider 的两段文本。
- `call_started` 和 `call_completed` 转发到端口；`finish.web` 并入 `done`。

**新增 `src/shared/latest-reminder.ts`**（纯函数）：按本机时区产出 `YYYY-MM-DD,<星期>,,Web,<语言>`。星期用 `Intl.DateTimeFormat` 按界面语言格式化，语言名取 `prompts.ts` 里新增的常量。后台不能引用 `i18n.js`，而语言名是发给模型的文本，放在 `prompts.ts` 里也符合它「发给模型的文字」的定位。

**新增 `src/shared/web-citations.ts`**（纯函数，后台和面板都能用）：

- `buildWebResult(serverToolCalls, annotations)`：把末块的数据整理成 `WebResult`。
  - 步骤按 `calls` 的顺序展开成 `WebStep[]`，`signature` 和每一步的 `reasoning_content` 丢掉。
  - 来源按网址去重，顺序按首次被引用。引用的网址到各步骤的 `sources` 或 `page` 里找标题；找不到时用引用自带的 `title`。
  - 次数按调用数算，不用 `usage.server_tool_use`（§3）。
- `insertCitationMarkers(markdown, citations)`：把码点偏移换算成字符串下标，在 `end` 处插入 `\uE000<编号>\uE001`。私用区字符是模型不可能输出的，所以不会和正文冲突。插入按 `end` 从大到小进行，先算好的下标不会失效。插入点在三种情况下后移（E-07、E-17）：落在 `*`、`_`、反引号这类定界符的中间，落在链接地址里，或者紧挨在句子的收尾标点之前。

### 5.4 面板：开关和设置

**`platform/settings.ts`**：`Settings` 增加 `webSearch: boolean`，默认 `true`。

**`WebSearchButton`**（放进 `ComposerParts.tsx`，在 `Composer.tsx` 里渲染在输入框和发送按钮之间）。点击切换 `webSearch` 设置。两种样子：

| 状态 | 样子 | 提示文字 |
|---|---|---|
| 开启（默认） | 主色高亮 | 联网搜索已开启（是否搜索由模型判断），点击关闭 |
| 关闭 | 和附件工具一样的安静图标 | 联网搜索已关闭，点击开启 |

**设置页**：大模型配置里加一个勾选框，放在智能体模式上方，带一句提示：默认开启；是否搜索由模型判断；需要 DeepSeek 官方接口的 `deepseek-flash`。文案进 `i18n.js`。

### 5.5 面板：回答展示

**流式期间**。`stream-store` 的 `LiveStream` 增加 `webSteps`。收到 `call_started` 就追加一行并标成进行中，收到 `call_completed` 就按 `call.id` 补上结果或错误（E-15）。

**结束时**。`stream-controller` 的 `finalize()` 把 `done.web` 挂到 assistant 消息上。流异常结束但已经有正文时，用已经收到的 `webSteps` 生成一份 `web` 保存，过程行不至于丢失。

**过程行**（新增 `WebTraceView.tsx`）。回答上方一行摘要，可展开：

- 进行中：`正在联网搜索…`，后面跟当前的查询词。
- 结束后：`已联网搜索 · 搜索 N 次 · 打开网页 M 个`。展开后每次调用一行，搜索下面列出结果卡片（标题加站点名，可点击）。

**角标**。`MarkdownView` 增加一个可选属性，接收来源和引用。渲染前先调 `insertCitationMarkers()`，消毒之后再遍历文本节点，把占位符换成 `<a class="web-cite">`。用链接而不是按钮，是为了让中键点击和右键菜单都能用。`AssistantBubble` 和 `LiveAnswer` 都接上。

因为占位符是在渲染时才插进来的，`msg.content` 始终是干净的。所以复制、朗读、分享图片、导出都不需要改（R-12）。

### 5.6 为什么不做接口能力探测

默认开启意味着每条消息都带工具。如果接口不支持，请求会失败。此前的方案为此设计了「先带着发，被拒就记住，再重发」，加上开关的第三种状态和一次性提示。

决策 ⑤ 之后这些都不需要了：唯一的端点就是 `deepseek-flash`，实测它接受工具并且会搜索。

保留的取舍是：换成别的接口或模型时会直接看到接口的报错（E-01）。实测 `deepseek-v4-pro` 的报错很清楚，写明了「请改用 deepseek-flash」。关掉开关就能恢复。

以后如果要支持其他接口，探测可以加在现有的降级循环里（`openai.ts:110-117`），那条循环本来就是为「接口拒绝了某个可选字段」准备的。

### 5.7 和智能体模式的关系

`send.ts` 组装请求时用一条判断：`agent: agentMode && !webSearch`。搜索开着，请求就走普通聊天加搜索；搜索关了，智能体模式照旧。

这样选有三条理由。第一，智能体模式已经确定要废弃，为它做两个工具机制的联动不值得。第二，两个机制同时跑没有验证过：智能体循环建立在 AI SDK 上，搜索事件和末块的引用要另外接进去，函数工具循环里的思考内容回传也是另一套规则。第三，实测两者一起声明时接口不拒绝（§6 的 E5），所以这是一个以后可以放开的产品选择，不是一条死路。

结果是：搜索开启时智能体模式不再生效（E-14，已确认接受）。

不做任何共存提示或界面。智能体模式废弃时，`agent-runner.ts`、AI SDK 依赖、`AGENT_TOOL_SPECS`、`agentTrace` 和设置页的勾选框可以一起删除。

### 5.8 不在本次范围内

- 其他接口、其他模型的适配和探测（决策 ⑤）。
- `deepseek_read_url`（让模型读取用户消息里的链接）。
- 强制搜索。接口不支持用 `tool_choice` 指定这个工具。
- 把独立的 Search API 做成通用工具。
- 展示图片搜索的图片。
- thinking 的设置界面。实测深度思考搜索 5 到 11 秒且回答略好，没有理由关掉它。

### 6.1 方法

- 时间：2026-11-23 凌晨（北京时间，空闲时段），模型 `deepseek-flash`，接口 `https://api.deepseek.com`。

### 6.4 质量对比

五个联网问题里，A 和 B 的事实都基本正确，A 略好。例如问「最新的模型」，A 多打开了四个网页，找到了「V4.1 Pro 正在灰测」；B 只答到 V4.1-Flash-1017。问「文章之后的新动态」时，A 按主题组织并回扣了文章，B 的细节更多但混进了一条未证实的传闻。

A 的代价是每条联网回答多花 1 到 8 秒，输出 token 是 B 的两到四倍。据此决定不关思考（决策 ④）。

翻译这道题上 B 的输出只有 A 的三分之一。这说明关掉思考影响的是所有回答，不只是联网回答，所以「快速模式」不能当作搜索的附属开关来做。

### 6.5 其他观察

- **`tool_search` 数的是查询词**。一次搜索调用带了两个查询词，用量里记 2；深度搜索打开了四个网页，`tool_fetch` 仍是 0。
- **每个联网问题只有一次搜索调用**，带 2 到 4 个查询词。深度搜索随后打开零到四个网页。这批运行里没有出现页内查找。
- **模型不搜索时没有任何进度事件**，`step_reasoning_done` 也没有。它只在真的调用工具时出现，并且关闭思考时也会发。
- **`call_completed` 会乱序**。同一步里第 2、3 个调用先完成。
- **引用网址和来源网址能精确对上**（两份夹具共 8 条引用全部匹配）。多条引用可以指向同一段正文（B 里三条引用的范围完全相同）。
- **末块**的 `delta.content` 是空字符串，`reasoning_content` 在思考模式下是 `null`，关闭思考时没有这个字段。
- **追问也可能触发搜索**。E3 的第二轮是「把你上面的回答压缩成三句话」，模型又搜了一次。这是唯一观察到的多余搜索。
- **样本的局限**：一篇文章，每题每配置只跑一次，模型输出有随机性。AC-02 留了一个的余量。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 模型过度搜索，日常问答变慢变贵 | 实测样本里没有发生，但样本小。AC-02 用同一组问题回归；追问类请求偶尔会多搜一次（§6.5） |
| 引用偏移破坏 Markdown 格式 | 插入点避让定界符和链接地址，并用测试覆盖加粗、斜体、行内代码、链接 |

## 9. 和 talktome 的取舍对照

| talktome 的做法 | 本方案 | 原因 |
|---|---|---|
| 开关默认关闭 | 默认开启 | 搜索是常态需求，且声明工具不等于一定搜索 |
| 往 system prompt 手写「今天是几号」 | 用官方的 `latest_reminder` | 官方机制就是为这个问题设计的，实测有效（§6 的 E4） |
| `messagesForWebSearch` 去掉开头的 assistant | 不需要 | `trimHistory` 已经保证历史不以 assistant 开头 |
| 忽略 `server_tool_event` | 转成进度事件 | 文字界面应该让人看到它在搜什么 |
| 不处理引用 | 按偏移渲染角标 | 阅读助手需要能核对出处 |
| 搜索时放宽超时（空闲 15 秒放到 45 秒） | 不放宽 | 本项目的空闲超时本来就是 90 秒，实测最长一次 11.4 秒 |
| 思考固定开启 | 不改思考参数 | 实测开着思考的联网回答更好，耗时也可以接受 |

### 11.2 对设计的两处调整

两处都来自端到端验证时看到的真实数据，不是事先计划的。

**角标放在句号之后（E-17）。** 捕获的真实流里，7 条引用全部在句子的 `。` 之前结束。按原设计，角标会落在句子里面，读作「……API”¹。」。现在放在收尾标点之后，读作「……API”。¹」。ASCII 句点后面不是空白时不后移，所以 `3.14`、`e.g.` 不会被当成句末。

**正文出现之前的断流自动重试一次（R-15）。** 见下一节的原因。只重试一次，并且只在还没有任何正文的时候：那时没有任何东西会丢。已有正文之后断掉、接口返回了 HTTP 状态码、空闲超时、面板已经关闭，这四种情况都不重试，走原有的路径。

### 11.4 一个与功能无关、但会影响体验的发现

端到端验证时，有的联网回答在正文出现之前就以 `network error` 失败。排查过程如下。

先排除了代理：我的 shell 里配了 `127.0.0.1:7890` 的代理，Chrome 会用它而 Node 不会。让浏览器直连之后，失败仍然出现。

然后在同一个浏览器里做对照：不经过扩展的任何代码，只用一个普通的流式 `fetch` 发同样的请求，分别在普通页面和 Service Worker 里各跑 8 次。

| 连接方式 | 中途断开的次数 | 协议 |
|---|---|---|
| 经代理 | 8 次里 4 次 | HTTP/2 |
| 直连 | 8 次里 2 次 | HTTP/2 |
| 阶段 0 的 Node 脚本 | 45 次里 0 次 | HTTP/1.1 |

断开都发生在数据正常流动的时候，之前已经收到了 300 字节到 380 KB。所以这是这台机器上浏览器到接口的长连接问题，和这次改动无关。

它和联网搜索有关系的地方在于：联网让一次回答的流从大约 30 KB 变成 300 到 440 KB，碰到断开的概率明显变高。这就是加 R-15（自动重试一次）的原因。注入故障的那次端到端运行验证了这条路径：同一个请求体被发了两次，面板提示「连接中断，正在自动重试…」，最后拿到的回答是完整的。
