## 3. 三个重点偏差的判定

### 3.1 偏差 1：E-06 机制替换（`data-final` 不存在）——**可接受**

设计原文："气泡无 `data-final` 标记前不响应"。独立核实结果：

1. **`data-final` 确实不存在**：全库 grep 仅 `features/share-image.ts:46` 注释提及。实现方没有虚构。
2. **结构保证成立**。`createTTSButtons` 唯一调用方是 `services/tts/index.ts:139 addTTSButton`（tts/index.ts:138-143，无条件转发）。`addTTSButton` 的全部调用方共 3 处：
   - `stream-handler.ts:366`：在 `finishAnswer` 内，而 `finishAnswer` 仅由 `finalize()`（260-287 行）在流终态调用——`finalize` 先置 `finished=true`、断开 port、移除 typing-indicator（266 行）后才走到 `finishAnswer`（287 行）。即按钮挂载时流已结束。`finishAnswer` 的两个非连接分支（349-356 隐藏 tab、359-362 气泡已脱离）均**不**调用 `addTTSButton`，由历史重渲染路径接管。
   - `chat-history.ts:256`（handleLoadChat）：渲染的是 IndexedDB 已保存会话，仅含完成消息。
   - `main.ts:163`：`ADD_TTS_BUTTON` 订阅方。**该事件全库唯一发射方**是 `dom-helpers.ts:506`，位于 `appendMessageFromHistory` 内且仅 assistant 消息；历史中的 assistant 消息只在 `finalize` 的 `appendHistory`（stream-handler.ts:278）之后才存在——流式中的回答不在 `conversationHistory` 里，故该路径不可能给流式气泡发按钮。流式期间 tab 切换回前台的 `reattach()`（stream-handler.ts:159-164）重挂的是原气泡节点，其上从无按钮。
3. **守卫有效且必要**：`features/share-image.ts:51` 检查气泡内 `.typing-indicator`。typing-indicator 由 `addTypingIndicator`（dom-helpers.ts:412-418）挂为 msgEl 子节点，在收到首条 thinking/chunk/tool_calls 时移除（stream-handler.ts:169/172/180）——该窗口期气泡本无按钮，守卫覆盖的是"首 token 前仍显示指示器"的残余状态，属纵深防御。

结论：设计意图"流式中点击被忽略"被完整满足——流式中按钮不存在（不可能点击）+ 指示器守卫兜底。机制不同、语义等价，且避免了为加标记而越出改动清单去改 stream-handler/dom-helpers。**判定：可接受，无需返工。**

### 3.2 偏差 2：i18n 增补 10 个 key（设计 8 + 2）——**可接受，必要性成立**

- `share.watermark`（`i18n.js:148/474`）：R-02 明确要求底部水印"由 X 生成"，代码库无同语义 key（`app.fullName` 只是应用名，无"生成"句式），而 R-07 禁止源码 CJK 字面量 → 此 key 为 R-02 ∧ R-07 的必然交集。**必要。**
- `share.filePrefix`（`i18n.js:149/475`）：AC-02 要求文件名前缀"小梨子"。复核 `app.fullName` zh 值为 `'小🍐子阅读助手'`（i18n.js:4）——含 emoji 且多"阅读助手"后缀，不能直接做文件名前缀；无其他现成 key → **必要**。（实现报告称"无 emoji 纯文字"的理由经查属实。）
- 双语成对：11 个 key（`action.shareImage` + 10 个 `share.*`）在 zh（128/140-149）与 en（454/466-475）一一对应，且有 22 例单测逐一断言双语言可解析。
- 附带观察（P-04）：en 界面文件名前缀为 `PearReader`，与 AC-02 字面"小梨子"不同。这是 R-07（禁 CJK 字面量）+ AC-06（双语）联合约束下的合理取舍，zh 界面完全符合 AC-02。**判定：可接受。**

### 3.3 偏差 3：`buildShareCard` 返回 HTMLElement，高度由 `fitShareCard` 产出——**可接受，行为等价**

- 设计 §4.2 签名 `{el, height}` 与设计 §4.1 管线"构建后挂 body 下 left:-9999px 测量实际高度"本就矛盾：未挂载的元素测不出高度。实现将"纯构建"（`buildShareCard`，jsdom 可测）与"测量拟合"（`fitShareCard(data, measure)`）分离，measure 由 services 层注入 `measureOffscreen`（services/share-image.ts:23-31）——恰是设计 §4.1 描述的"挂 body、-9999px、读高、立即移除"。**语义等价且可测性更好。**
- E-01 三级级联**真实实现且被测试覆盖**：`fitShareCard`（share-card.ts:185-205）① 先做 12000 字符软截断（与设计 §4.2"先按段落累积"顺序一致）→ ② 实测高 >16000 则 560 宽重建 → ③ 仍超则从**原始** markdown 按 6000 硬截断并置 `truncated:true`（脚注 156-161）。截断与否以脚注节点为准（203 行），单一事实源。
- 测试覆盖三级全路径：`share-card.test.ts` "falls back to 560px…"（级 ②）、"hard-cuts with a footnote…"（级 ③，'x'.repeat(8000) + 恒超测量，同时覆盖单段落超限的字符切割回退 59 行）、"keeps 720px…"（不触发）。段落边界完整性有独立断言（145-155：输出必为完整段落前缀）。**判定：可接受。**
